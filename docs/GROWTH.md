# 移动端编辑、删除恢复与规模增长评估

核对日期：2026-10-15。**这是调研结论与候选方案，不是新增功能已经上线。** 以 Sveltia CMS 0.235.1、Hugo 0.167.0 和当时尚未发布的体验扩展工作区为实验基线；站内搜索、文字分享图等已随 2026-10-19 更新交付，不属于原 v1.0。下面的手机手势、回收站、语义地址与规模替换方案仍是研究候选。

## 结论先行

1. 手机列表快捷操作值得做，但优先提供可见的「更多」入口，再把左划作为快捷方式；不要让手势成为唯一入口，更不要划一下就执行删除。
2. 已提交的文件通常能从 Git 历史恢复。现阶段优先补清楚恢复流程和独立备份，不急着维护完整回收站；Git 历史不等于手机上一键恢复，也不等于不可丢失的备份。
3. 语义地址可选、首次发布后固定；文件 ID 与公开地址分开，旧地址默认不迁移。不建议改成「标题一变，网址跟着变」。
4. 首页已有分页。千篇规模更早遇到的瓶颈是**全文搜索索引、全量归档、CMS 首次读库、图片及构建/仓库体积**，不是静态文章页本身。
5. 不因「可能上千篇」立即引入数据库、自建后台、远程搜索或 R2；先用可测量的体积、延迟和额度决定迁移时点。

## 1. 已有能力和真实缺口

| 层面 | 已有实现 | 边界 |
|---|---|---|
| 访客首页 | Hugo 分页，每页 12 篇，第一页最多另列 3 篇精选 | 不是把所有正文或图片一次发给访客 |
| 归档 | 按年/月分组，全部文章输出在同一页 | 分组不等于分页；折叠已输出的 HTML 也不减少下载和节点数 |
| 待发布搜索 | 首次搜索才下载同源全文 JSON；最多显示 20 个结果；2 MiB 原始索引上限 | 20 个结果不等于只下载/扫描 20 篇。超过上限会阻止整个构建，不会静默丢弃正文 |
| CMS 列表 | 上游使用 `InfiniteScroll` 渐进渲染，支持搜索、排序、筛选 | 不是后端按页取文章。Git 后端首次仍下载/解析所管理的条目文本，之后利用浏览器缓存；不能把渐进渲染当成内存有界的虚拟列表 |
| 手机删文 | 详情页菜单有删除和二次确认 | 0.235.1 的小屏列表不渲染删除按钮，勾选框在小/中屏也不渲染 |
| 删除/恢复 | simple 模式的删除形成 Git 提交，随文章存放的媒体可能一起删除 | 没有项目级「回收站/一键恢复」；未提交的输入不受 Git 历史保护 |
| 稳定链接 | 文章文件夹 ID 决定默认网址；改标题不改链接 | 单加文章 front matter 的 `slug`，在当前 `:contentbasename` 配置下不会改变文章网址 |

手机入口已用固定主程序及其 SRI 校验值做离线浏览器复现：1280px 有列表勾选和删除，390px 没有；手机详情页的删除确实弹出确认，取消后文件仍在。仅使用临时 test-repo，不涉及真实 GitHub 写入；不是 iPhone/Safari 实机证明。

## 2. 手机体验：先解决操作，再选择实现层

### 建议交互

- 点整行继续进入编辑；每行可见的「⋯」提供编辑、撤下/恢复公开、删除等实际支持的操作。左划只展开同一组操作，不触发提交。
- 左划为增强能力，键盘、屏幕阅读器、鼠标和不会手势的用户仍可操作。建议触控目标至少 44×44 CSS 像素。
- 只有明显横向动作才打开操作区；保持纵向滚动、系统边缘返回、输入框选择和缩放可用。同一时间最多展开一行。
- 删除复用 CMS 的确认和存储流程。确认应明确对象及随文媒体的处理，默认焦点留在安全操作；取消返回原行。
- 删除进行中禁止重复提交；失败保留条目并明确提示。网络超时可能发生在服务端已经提交之后，先核对远端状态，不能盲目重试。
- 编辑返回时保留搜索词、筛选和滚动位置。草稿/已公开状态、保存中/已提交/部署失败应区分清楚。
- 移动端再检查软键盘遮挡、底部安全区、工具栏横向空间、中文输入法、上传进度和未保存离开提示。不要为了删文入口重做整个编辑器。

### 实现选择与成本

| 路径 | 适合做什么 | 判断 |
|---|---|---|
| 模板 CMS 配置 | 字段顺序、提示、列表摘要、筛选/分组、减少日常选择 | 低成本，但不能凭配置新增列表左划 |
| 上游已有/新增的原生能力 | 手机更多菜单、选择模式、滑动操作 | 优先检查版本说明、提出上游改进；是否存在合适版本和合入时间均不保证，不自动升级 |
| 小范围维护上游分支 | 修改列表组件，复用权限、关联资源、并发检查、错误反馈 | 可实现，成本中高；每次升级要重放补丁并测手机、键盘、删除与冲突，需另行接受这项维护责任 |
| 给压缩后的 CMS 注入 DOM 补丁 | 按内部类名/节点和事件模拟按钮 | 不推荐。界面结构不是稳定接口，容易把行号、选中条目、权限或删除状态对应错 |
| 另建 GitHub 写入界面/后台 | 完全自定义体验 | 本需求收益不足以抵消认证、令牌、媒体、冲突、批量操作和升级维护成本 |

本版公开 API 支持字段、正文组件、预览和事件等扩展，未发现稳定的「替换条目列表/注册左划操作」接口。现有 `editor-components.js` 只扩展正文组件，访客站 `custom.js` 也不是后台列表扩展点。**不能把本需求估成加几行 CSS，或为赶进度绕过原生保存/删除校验。**

## 3. 删除、撤下、回收站与备份

### 四件事不要混为一谈

| 动作 | 当前源文件 | 当前网站 | 能否恢复 |
|---|---|---|---|
| 打开 `draft` 后保存 | 保留文章和图片 | 成功部署后不再发布该文章及其未被其他页面引用的资源 | 关闭草稿后重新保存/部署；最适合「暂时不想公开」 |
| CMS 删除已保存条目 | 新提交移除条目；本项目文章使用随文媒体目录，相关媒体也可能移除 | 成功部署后移除 | 删除前版本仍在可访问的 Git 历史里时，可以恢复 |
| 清理未保存输入/浏览器数据 | 可能尚无 Git 版本 | 没有新增线上版本 | 只能依赖仍存在的本机草稿，不能承诺从仓库找回 |
| 仓库/历史被删除或强制改写 | 远端历史可能不可用 | 不一定立即改变当前部署 | 需要独立保留的备份；普通历史查询不再足够 |

**CMS 显示删除成功，不等于网站已成功下线。** 例如其他正文仍链接被删文章，当前 `check-site` 会阻止构建，旧网站版本可能继续在线。撤下敏感内容时必须检查构建结果、实际页面、图片和订阅源，而不是只看列表消失。

本版 Sveltia 会识别随条目存放的资源，删除流程还包含 Relation 字段的关联处理；这不等于能识别任意 Markdown 链接或外站引用。共享 `assets/media/` 不能按「删了某篇」就整批清理。跨文章复用另一篇文章目录里的图片也会增加误删和断链风险，真正共享的图应放共享目录。

### 恢复方法

在**另外的干净克隆或临时分支/工作区**中处理，先确认最新远端和目标路径没有新文件，避免覆盖当前未提交工作：

1. 用 `git log --all --diff-filter=D --summary -- content/posts/` 找删除提交；检查提交范围，确认删除前的正确版本。
2. 从该版本恢复准确的文章目录，而不是重置整个仓库：

   ```sh
   git restore --source=<删除前提交> -- content/posts/<文章ID>/
   ```

3. 同时核对随文图片、必要的共享资源与引用。**恢复旧文章会带回旧的 `draft` 值，建议先设为 `true`**，避免恢复操作意外重新公开。
4. 检查 diff、运行构建/媒体检查，再作为一个新的恢复提交保存。确认上线意图后再推送；simple 模式推送会触发既有构建。

不使用 `reset --hard` 或强推旧镜像；若一次删除提交混有其他改动，也不要不检查就整笔 `revert`。Git 历史恢复是「取回文件」，不是抹掉曾公开的副本。

### 回收站的取舍

**当前建议：二次确认 + 草稿撤下 + 可操作的 Git 恢复说明 + 独立快照。** 若手机上频繁删改，且需要不找开发者就能恢复，回收站的价值会上升，届时再作为独立功能验收。

真正的回收站至少需要：删除状态与时间、独立列表、文章和随文媒体原子处理、恢复路径冲突检查、恢复默认草稿、搜索/RSS/归档/sitemap/图片的发布隔离，以及清空时的强确认。仅加一个 `deleted: true` 字段，Hugo 不会自动停止发布；把文件移出 `content/` 还会改变 CMS 管理与媒体检查范围，也不是现成方案。

暂不添加自动「30 天后清空」任务：会增加误删、保留策略、触发器和费用，且删当前文件不会让 Git 历史立刻变小。回收站清空也不代表 Git、备份和第三方缓存中的副本已清除。

`scripts/backup.sh` 是跟随远端更新的镜像，**不是不可变快照**。它执行 `remote update --prune`；若远端历史遭改写，继续同步可能失去旧引用，不能寄希望于未引用对象永远保留。应另行手工保留带日期、不要原地覆盖的 bundle/镜像快照及离线副本；包含私人内容的备份同样需要保护。这里未新增备份自动化。

## 4. 语义化链接：生成器层容易，迁移和长期维护需克制

`slug` 指供人阅读的网址片段，例如 `/posts/rainy-walk/`。它改善分享时的可理解性和人工辨认；Google 的 URL 指南也推荐简单、可描述的词语。但它不是排名提升保证，也不会自动加速构建、解决分页或增强权限。

### 推荐：稳定文件 ID + 可选固定 slug

```text
源文件：content/posts/20261015-a1b2c3d4/index.md
无 slug：/posts/20261015-a1b2c3d4/
显式 slug 为 rainy-walk：/posts/rainy-walk/
```

Hugo 可把文章 permalink token 从 `:contentbasename` 改为 `:slugorcontentbasename`：填了 slug 就用它，否则沿用目录 ID。隔离实验已确认这能保留无 slug 的旧地址，改标题也不改变显式 slug，重复地址被当前路径校验阻止。**实验未修改正式配置，也未完成 CMS 新字段的保存往返验收。**

CMS 集合里的 `slug` 模板控制文件 ID，Hugo front matter 的 `slug` 控制公开地址，是两个层面。不能把现有 CMS 的「改 Slug/文件路径」操作当成上述地址解耦方案。

建议新文章按需填写，首次发布后不自动跟随标题；普通页面也要有保留路径和冲突校验。标题重复时人工修正或附短 ID，而不是静默覆盖。可先以小写英文/拼音和短横线为默认；中文网址本身可用，但复制、百分号编码、Unicode 规范化和输入成本都要考虑，不能声称中文不利于搜索。

### 收益与代价

- **收益**：链接更易读、更容易辨认内容；源文件和图片目录仍稳定。
- **代价**：作者要起名；需要大小写/Unicode/重复/保留路径校验；改地址要维护旧链接与跳转；标题、地点、人名可能通过 URL 泄露更多信息。随机 ID 也不是访问控制。
- **长期成本**：旧 URL 涉及外链、书签、正文链接、分享缓存和 RSS。当前 RSS 把永久链接作为 GUID（订阅条目的身份标识），改变旧地址可能被阅读器识别成新文章。

不建议批量迁移旧文章。确需改名时：同步 canonical、站点地图、站内引用及图片地址，保留旧地址跳转，检查无循环/多级跳转、草稿和删除后的行为。

Hugo 默认 `aliases` 生成的是带 `meta refresh` 的 HTML，**不是 HTTP 301**。Cloudflare 静态资源支持 `_redirects`，可以实现真正的 301，但需要生成/维护规则和本地检查；当前 `check-site` 不能直接把「只存在于 `_redirects` 的旧地址」当作已存在文件。官方上限为 2,000 条静态、100 条动态规则，合计 2,100，别把无上限改名当成免费能力。

## 5. 百篇、千篇的本地实验

使用临时合成站点，不复制作者文章/照片，不访问 GitHub 或云端构建。每篇正文恰为约 1,000 个中文字符，标题各不相同，无正文图片，开启默认文字 OG（Open Graph，社交分享预览）图。Hugo 0.167.0、Node 24.18.0，`GOMAXPROCS=2`；每组冷构建用独立缓存。

| 文章数与搜索状态 | 首页条目 | 首页 HTML | 归档 HTML | 原始全文索引 | Hugo 冷构建 |
|---|---:|---:|---:|---:|---:|
| 100，搜索开 | 12 | 18.4 KB | 88.3 KB | 346.5 KB | 5.7 秒 |
| 500，搜索开 | 12 | 18.5 KB | 416.3 KB | 1.73 MB | 24.2 秒 |
| 1,000，搜索开 | — | — | — | **超过 2 MiB，构建失败** | 约 48 秒后报错 |
| 1,000，仅实验关闭搜索 | 12 | 16.9 KB | 825.9 KB | 无 | 49.7 秒 |

KB/MB 为十进制原始字节量，2 MiB 是 2,097,152 字节；不是网络压缩后的传输量。1,000 篇成功产物有 2,111 个文件、约 57.3 MB；站内产物检查另用约 0.65 秒。同一夹具保留图片处理缓存后的热构建约 2.2 秒。

这些数值**不是手机体验、GitHub 首次加载、云端耗时或账单保证**。`GOMAXPROCS=2` 也不是对两颗独占 vCPU 的仿真；冷/热差异主要提示需要核查图片/OG 缓存，不可直接外推云端性能。Workers Builds 的官方默认框架缓存清单未列出 Hugo `resources/_gen`，不能假定本地热缓存收益在线上同样存在。

以本组正文估算，搜索约六百篇就可能触限；长文会更早，短记会更晚。因此应看**索引字节量而不是文章数**。目前只验证了正确失败，没有调高上限或关掉正式搜索。

## 6. 建议的增长方案

### 阅读与检索

1. **保留首页 12 篇分页**，不替换成无尽滚动。需要时增加有界的页码或按年份跳转，避免翻几十页找旧文。
2. **归档分层**：`/archive/` 只列年份、数量及入口，各年独立页面；单年太多再分页。只加折叠按钮不会减少已输出的 HTML。保留能直接访问、可被抓取的链接，以及无 JS 导航。
3. **搜索提前设迁移点**：建议原始索引接近 1 MiB 时开始评估，不等到 2 MiB 挡住发布。短期可由作者明确排除不需检索的页面；不能悄悄只索引前几百字再声称全文搜索。
4. **首选对照候选是 Pagefind**：构建后生成分块静态搜索索引，同源按需加载，不需要搜索服务或 API 密钥。它的中文分词与当前任意子串匹配不同，必须对照短词、中文、代码、无结果和排序；还要验证运行资源与 CSP、排除草稿/noindex/search_exclude、内容区提取、旧索引切换和无 JS 降级。固定依赖版本，不把 `npx latest` 下载塞入每次发布。官方大站性能示例不是本站实测值。

不推荐手写「按年份拆全文 JSON，然后全下载再搜索」：这可能只是把一个大请求拆成多个，并没有降低总量；如果只搜当前年份，则必须向用户明确检索范围。

### CMS 管理

先把搜索、草稿/类型筛选、时间排序和适度的年/月分组用起来，减少靠滚动查找；配置只能优化导航与渲染，不能自动消除第一次读库的全量成本。检查分组是否同时创建太多可见分块。

分别量一次空缓存登录、热缓存登录、手机过滤/输入延迟、浏览器内存和图片缩略图请求，再决定是否需要上游的真分页/虚拟化。虚拟列表只保留可视区附近的界面节点，不等于后端不取全文；前后两层必须分开测。不承诺「每页 50 条」会自动减少 GitHub API 请求。

上游 GitHub 后端使用递归 tree 列表与分批 GraphQL 文本请求，已有截断处理与缓存；不是 Contents API 单目录返回 1,000 项就意味着本站最多 1,000 篇。但 API 主/次级速率限制仍存在，网络失败、令牌过期和首次全量下载都需要清晰反馈，不能无限重试。

### 图片、构建与费用

- 仓库体积比文章数更关键。例如 **1,000 篇 × 5 张 × 每张 300 KB ≈ 1.5 GB**，还没算历史版本。删当前照片不会清空历史占用。GitHub 建议仓库理想情况下小于 1 GB、强烈建议小于 5 GB；这是健康建议，不是统一硬容量上限。
- 继续保留上传前压缩/去元数据、发布重编码和源/产物检查。不要为加速跳过隐私校验；共享素材不自动按「似乎未用」删除。
- 每张较大正文图最多生成三档响应式尺寸，另有每篇分享图。**1,000 篇 × 6 张 × 3 档 = 18,000 张衍生图**，加文章 HTML、OG 和分页，可能超过 Workers Free 每版本 20,000 个静态文件上限。Paid 为 100,000；单文件均为 25 MiB。应统计最终文件数，不只统计源照片。
- R2 仅在仓库/Git 操作真正吃紧时评估，见 [R2_FUTURE.md](R2_FUTURE.md)。迁移涉及上传凭证、草稿图片是否提前公开、独立备份、缓存和请求/存储计费；不是切一个 provider 就完成。
- simple 模式每次保存，包括草稿，都可能触发现有生产构建。粗算 `每月构建分钟 ≈ 触发次数 × 单次分钟`；例如每天 20 次、每次 1 分钟、30 天为 600 分钟，还要加账户其他项目、失败和重试。实际以服务计量为准。
- 本次复核的 Workers Builds 规则：Free 3,000 分钟/月、1 并发；Paid 含 6,000 分钟/月，超出 $0.005/分钟、6 并发；20 分钟超时，额度按账户共享。账户剩余额度仍需控制台确认。不要为了自动草稿保存频繁提交 main，不引入第二套 Actions 发布或无人值守重试。
- 静态资源请求免费不限量，不代表 Worker 脚本执行、构建、存储外迁或第三方 API 都无限免费；保持当前纯静态服务方式。

## 7. 按风险排列的落地顺序与验收

以下是建议，不是已承诺开发排期；每个分片独立决定是否实施。

| 顺序 | 分片 | 验收重点 |
|---|---|---|
| 0 | 收尾发布既有更新 | 先核对最新远端，保护作者新增/删除的文章和配置；合并后测试，不从落后的本地工作区直接部署。只提交已确认范围 |
| 1 | 删除/恢复说明与手机快捷入口 | 先完成信息与交互设计，再决定上游/维护分支方案；测试取消、重复点击、断网、提交后超时、权限不足、两设备修改、关联资源和焦点恢复 |
| 2 | 有界归档与容量提示 | 100/500/1,000 篇，首页条目有界、归档节点不无限增长、无重复/漏文；零 JS 可读；大索引在耗费大量图像处理前给清晰诊断，不降低既有防线 |
| 3 | 可选固定语义地址 | 旧地址不变、改标题不改地址、碰撞/保留路径失败、图片/内链/RSS正确；需要迁移时验证真正跳转与回退 |
| 4 | 搜索替换、CMS 深度优化或 R2 | 由索引大小、低端真机延迟、API/仓库/产物额度触发，分别实验，不捆成一次大迁移 |

建议的**调查阈值**：搜索原始索引接近 1 MiB、归档原始 HTML 达数百 KB、仓库接近 500 MB–1 GB、产物文件达到套餐上限约 70%、冷构建达到数分钟或共享分钟明显吃紧。它们是提前看数据的信号，不是新增硬限制，也不是只要没过线就保证流畅。

仍未验证：iPhone/Safari 手势与软键盘，低端手机千篇后台，真实 GitHub 冷/热加载，带大量独立图片的构建，Pagefind 在本站的中文匹配/CSP，以及云端 Hugo 缓存与账户剩余额度。本轮没有安装新依赖、修改自动化、提交、推送、部署或执行真实删除/恢复。
